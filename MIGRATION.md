# Migration roadmap — status: complete

**All 116 files of the original Enterprise ITSM Tool have been migrated.** This
document is kept as-is, phase by phase, as the record of how it happened and
why each deviation was made — see the closing note at the end of the Phase 5
section for the full picture.

Phase 1 ported **Config, Common, Security, and the Incident Register
module**. Phase 2 ported **Service Requests (with approval workflow),
Problems, Changes (with CAB approval), Assets, CMDB, Knowledge Base
(with version history), and cross-module Reports**. Phase 3 (done)
ported **Admin & Identity — user management, the permission matrix
editor, Master Data (Departments/Locations/Categories/SLA Matrix), and
role-based sidebar visibility** — 15 of the original 116 files. The rest
of the original project is preserved in `../original-source/` (all 116
files, exactly as exported from Apps Script) so every future phase has
the real logic to port from, not a guess.

The remaining files fell into four natural phases, tackled in this order:

## Phase 2 — Finish core ITSM (done)

- `ServiceRequestEngine.gs` → `src/models/ServiceRequest.js`, `src/controllers/serviceRequestController.js`, `src/routes/requestRoutes.js`, `views/requests/*` — approval workflow (single + bulk decide) included.
- `ProblemEngine.gs` → `src/models/Problem.js`, `src/controllers/problemController.js`, `src/routes/problemRoutes.js`, `views/problems/*`.
- `ChangeEngine.gs` → `src/models/Change.js`, `src/controllers/changeController.js`, `src/routes/changeRoutes.js`, `views/changes/*` — CAB approval + implementation status + PIR close included.
- `AssetEngine.gs` → `src/models/Asset.js` + `AssetHistory.js`, `src/controllers/assetController.js`, `src/routes/assetRoutes.js`, `views/assets/*` — issue/return/decommission with history log included.
- `CMDBEngine.gs` → `src/models/ConfigurationItem.js`, `src/controllers/cmdbController.js`, `src/routes/cmdbRoutes.js`, `views/cmdb/*`.
- `KnowledgeEngine.gs` → `src/models/KnowledgeArticle.js`, `src/controllers/knowledgeController.js`, `src/routes/knowledgeRoutes.js`, `views/knowledge/*` — version history embedded per-article instead of a second collection.
- `ReportEngine.gs` → `src/controllers/reportController.js`, `views/reports/index.ejs` — SLA Compliance, Monthly Volume, Engineer Performance, Ticket Aging, Department Workload, Asset Warranty Expiry. The HR-dependent reports (Headcount, Attrition, Training Completion, Contract Expiry, Executive Summary) need the Phase 4 HR suite first.

Not yet ported from the original Phase 2 scope — need infrastructure this app doesn't have yet:
- `RecordEngine.gs`, `AttachmentEngine.gs` — shared record/attachment helpers (file upload storage isn't wired up yet; `multer` is installed but unused).
- `EmailEngine.gs` — needs a real email provider now (Apps Script used `MailApp`/`GmailApp` for free; a free-tier transactional email API like Resend or Brevo replaces it). Approval/decision events are currently recorded in history + the audit log instead of emailing anyone.
- `PublicIntake.html` + the public-form part of `IncidentEngine.gs` (honeypot + CAPTCHA + rate limit) — needs a CAPTCHA library (e.g. `hcaptcha` free tier).

## Phase 3 — Admin & identity (done)

- `AdminEngine.gs` → `src/controllers/adminController.js`, `src/routes/adminRoutes.js`, `views/admin/*` — user management (create/edit, role + department, activate/deactivate, password reset — no email provider yet, so an admin sets the new password directly) and the permission matrix editor (toggle grid of action × role, backed by the `Permission` collection). The original's safety guard — Administrator can never lose `admin_manage_settings`/`admin_manage_users` — is enforced server-side (those two checkboxes are also disabled in the UI), plus an equivalent guard preventing the *last active Administrator* from being demoted or deactivated by anyone (there's no sheet to hand-edit as a fallback here, so locking everyone out would be unrecoverable without direct database access).
- `MasterDataEngine.gs` → `src/controllers/masterDataController.js`, `src/routes/masterDataRoutes.js`, `views/masterdata/*` — generic config-driven CRUD, same shape as the original's `MASTER_DATA_SHEETS`, covering Departments, Locations, Categories, and the SLA Matrix (this is where you set your **real** SLA hours, replacing the seeded defaults). "Roles" wasn't carried over as an editable table — roles are a fixed enum wired directly into the permission system (`config/constants.js` → `ROLE`), so there's nothing free-form to CRUD there; changing the role list is a code change, same as it effectively was in the original once `Security.gs` referenced role names directly.
- The `moduleVisibility` block in `Navigation.gs` → `src/middleware/moduleVisibility.js`, wired into `views/partials/header.ejs` — a sidebar link disappears entirely once a role has zero permissions left for that module (toggle it off in the new Permission Matrix and watch it vanish for that role), instead of staying as a dead link that just 403s.
- `Setup.gs`, `MakeMeAdmin.gs` — reviewed, not ported: their entire purpose (seed default rows, force one account to Administrator when you're locked out) is now handled automatically by `server.js`'s auto-seed-on-boot, plus the new Admin Console itself is the safe way to fix a role from now on.
- `QuickFix.gs` — reviewed, not ported: it's a one-off script for seeding 6 named conference rooms, unrelated to Admin/Identity — it belongs with Room Booking in Phase 5 if that data is still wanted then.
- `Navigation.gs`, `Style.html`, `Index.html`, `SignIn.html`, `Welcome.html` — reviewed, confirmed fully superseded by Express routing + `views/partials/header.ejs`/`footer.ejs` + `views/login.ejs`. Nothing else worth carrying over — the original's page-shell/menu logic is what `moduleVisibility` above already replaces, and the sign-in flow here uses a real login form instead of Google identity + a company-domain check (that domain check doesn't apply — logins are now app-level accounts, not Google accounts).
- `DriveConfigEngine.gs`, `BackupEngine.gs`, `MonitoringEngine.gs` — still deferred; re-think rather than port literally (e.g. backups become `mongodump` on a schedule, not a Drive export). Not blocking anything — revisit once there's real data worth backing up on a schedule.

## Phase 4 — HR suite

The largest remaining chunk, 20 modules — being delivered in sub-phases
(4A, 4B, …) rather than one giant update, same reasoning as grouping
ITSM's remaining modules into Phase 2: each sub-phase is a coherent,
testable slice instead of one enormous untestable drop.

### Phase 4A — Employee lifecycle core (done)

The foundation everything else in this phase builds on: a real employee
directory, self-service, and the onboarding/offboarding lifecycle.

- `EmployeeEngine.gs` → `src/models/Employee.js`, `src/controllers/employeeController.js`, `src/routes/employeeRoutes.js`, `views/employees/*` — full directory CRUD. Status-driven automation ported exactly: setting Status to "New" auto-creates onboarding Service Requests + an Onboarding checklist (+ Admin Onboarding checklist, on create only — matching the original's own asymmetry between `createEmployee()` and `updateEmployee()`) + a login; setting Status to "Left" auto-creates offboarding Service Requests (flagging any assets still assigned to them) + an Offboarding checklist + deactivates their login. Directory reads are open to any signed-in user (matches the original — `getAllEmployees()` had no permission check at all); create/edit are HR-team gated.
- `OnboardingEngine.gs` (checklists + resignations) → `src/models/Checklist.js`, `src/models/Resignation.js`, `src/models/ExitInterview.js`, `src/controllers/checklistController.js` + `resignationController.js`, `views/onboarding/*` + `views/resignations/*` — the four checklist sheets (Onboarding/Offboarding/Admin Onboarding/Admin Offboarding) became one collection with a `type` field; Resignations keep the same 5-way IT/Finance/HR/Manager/Admin clearance tracking, with the same auto-complete-on-all-clearances behavior (employee status flips to "Left", login deactivated) plus the structured Exit Interview form.
- `ProfileEngine.gs` → `src/controllers/profileController.js`, `views/profile/index.ejs` ("My Profile") — aggregates the signed-in user's Employee record + assets currently assigned to them. Matches by email against the Employee Directory (more reliable than the original's name-matching, since this app's logins already carry a canonical email). Leave balance and Trainings sections are placeholders — see Phase 4B/4D below.
- `OrgChartEngine.gs` → `src/controllers/orgChartController.js`, `views/orgchart/index.ejs` — same "Reports To" name-based hierarchy, anyone without a resolvable manager becomes a top-level root.
- `MyWorkEngine.gs` → `src/controllers/myWorkController.js`, `views/mywork/index.ejs` ("My Work") — My Tickets (incidents/requests where you're the reporter/requester or assigned engineer) + My Approvals (pending Service Requests/Changes you can act on) + a personal snapshot. Leave approvals will join this list once Phase 4B ships.
- `Security.gs`'s `isHRTeam()`/`isITTeam()`/`isAdminTeam()` → `src/utils/teamAccess.js` — the other half of the original's access model besides the Permission Matrix: some actions are gated by "does this person actually work in that team" (Department **and** Role together — Administrator, or Manager + the matching department), not just "can this role do this action." This directly extends the "department-wise access" requirement from Phase 3 to modules where a plain role check isn't enough (an IT Manager shouldn't manage HR's employee records just because they're a Manager).

Deliberately deferred within 4A, both because they depend on infrastructure this app doesn't have yet (same reasoning as Phase 2's RecordEngine/AttachmentEngine/EmailEngine deferral):
- `PreOnboardingDetailEngine.gs` (BGV vendor emails, IT-provisioning emails, a document vault with base64 uploads, a Welcome Kit sub-checklist) — needs both an email provider and file-upload storage, neither wired up yet.
- The automatic No Dues Certificate generation-and-email on resignation completion — needs a letter/PDF generator and an email provider. Completion is recorded in the audit log instead, same as every other "would have emailed someone" point so far.
- Auto user provisioning had to change shape, not just get deferred: the original could create a login with zero password because identity came from Google Sign-In; this app authenticates with email + password (no Google Workspace/SSO dependency — keeps everything free), so provisioning now generates a one-time temporary password shown once to whoever created the Employee record (a flash message), the same pattern as the auto-seed Administrator password printed to the server log on first boot.

### Phase 4B — Leave, Attendance & Shift (done)

- `LeaveEngine.gs` → `src/models/LeaveRequest.js`, `src/utils/leaveBalances.js`, `src/controllers/leaveController.js`, `views/leave/*` — apply/approve/reject (+ bulk decide) same as the Service Request/Change approval workflows; the four-balance calculation (Casual/Sick/Earned/Unpaid) is ported exactly, including Earned Leave's real accrual rule (a day only counts if the employee checked in AND it was a weekend/holiday AND they weren't actually rostered to work it). `leaveType` is tightened from free text to a fixed enum (`config/constants.js`'s `LEAVE_TYPE`) — the original's balance math already assumed exact strings like "Casual Leave", so a typo there would have silently broken someone's balance; this just makes that assumption explicit. Leave quotas (18/12/30 days) are fixed constants for the same reason `MIGRATION.md`'s Phase 3 SLA defaults were: the original read them from a "Settings" sheet with these numbers as the fallback, and there's no generic Settings screen here yet — genuinely adequate for a small company in the meantime.
- `AttendanceEngine.gs` → `src/models/Attendance.js`, `src/controllers/attendanceController.js`, `views/attendance/*` — same honor-system Check In/Check Out (not biometric/geofenced), same identity guarantee (you can only check yourself in/out — the employee name comes from your session, never from a form field). Viewing everyone's attendance is gated to `reports_view`, matching the original's `getAllAttendanceSafe()`.
- `ShiftEngine.gs` → `src/models/Shift.js` + `RosterEntry.js`, `src/controllers/shiftController.js`, `views/shifts/index.ejs` — shift definitions + a date-range roster; assigning a shift replaces any existing roster entry for that employee+date rather than double-booking them, same rule as the original.
- My Profile's Leave Balance section and My Work's Leave Approvals (both placeholders in 4A) are now wired to real data; the dashboard's "Pending Approvals" count now includes pending leave requests too.

Deferred within 4B, same email-provider reasoning as everywhere else: notifying a manager by email when leave is submitted, and notifying the employee by email on the decision (both recorded in the audit log instead), and Security.gs's approval-delegation mechanic (a Manager/Admin going on leave can name a delegate who temporarily inherits their approval rights) — the "Delegate To" field is captured and stored on the leave request, but doesn't do anything yet server-side.

### Phase 4C — Recruitment & referrals (done)

- `ATSEngine.gs` → `src/models/JobPosting.js` + `Candidate.js`, `src/controllers/recruitmentController.js`, `views/recruitment/*` — job postings + a candidate pipeline (Applied → Screening → Interview → Offer → Hired/Rejected). Moving a candidate to "Hired" automatically starts their Pre-Onboarding checklist, same as the original — which meant picking that checklist type back up: it turned out to belong to `OnboardingEngine.gs` itself (not the deferred `PreOnboardingDetailEngine.gs`), so it's now a 5th `CHECKLIST_TYPE` alongside the four from Phase 4A. Only the checklist (task tracking) is ported — the actual work behind each task (emailing a background-check vendor, emailing IT, a Welcome Kit sub-checklist) still needs `PreOnboardingDetailEngine.gs`'s email/document infrastructure and stays deferred.
- `ReferralEngine.gs` → `src/models/Referral.js`, `src/controllers/referralController.js`, `views/referrals/*` — any employee can refer a candidate for an open posting; the recruitment team tracks status and reward payout. **Bug fix vs. the original**: `addCandidate()` there unconditionally required `recruitment_manage`, but `submitReferral()` (open to every role) called it directly to drop the referred candidate into the pipeline — so in the original, anyone without `recruitment_manage` submitting a referral would hit a permission error *after* their referral was already recorded, a confusing half-success. This port splits that into an ungated internal function (used by both the referral flow and the guarded "add a candidate" route) plus the permission check only on the direct route — the same internal/public split already used for onboarding checklists.

Deferred alongside `PreOnboardingDetailEngine.gs` (see Phase 4A): the automatic hand-off details (BGV/IT-provisioning emails) that would normally follow a "Hired" stage change.

### Phase 4D — Performance & growth (done)

- `PMSEngine.gs` → `src/models/Goal.js` + `Review.js`, `src/controllers/performanceController.js`, `views/performance/*` — goal tracking (with progress %) and formal review cycles (rating + written feedback). Reading the goal/review lists is open to any signed-in user (matches the original — `getAllGoalsSafe()`/`getAllReviewsSafe()` have no permission check); *creating* a goal or review is HR-team gated (`requireHRTeam`), same as Employee Directory management. Updating a goal's progress and acknowledging a review use a real **ownership check** ported exactly from the original — only the employee the record belongs to, or the HR team, can act on it — rather than a blanket permission.
- `SuccessionEngine.gs` → `src/models/SuccessionPlan.js`, `src/controllers/successionController.js`, `views/succession/*` — tracks key roles, their current holder, and up to two rated successors ("Ready Now" / "1-2 Years" / "3+ Years"). **Bug fix vs. the original**: every function in `SuccessionEngine.gs` called `requirePermission("view_reports")`, but `"view_reports"` was never actually defined anywhere in `DEFAULT_PERMISSIONS_MAP` (the real key used everywhere else for the Reports module is `"reports_view"`) — so in the original tool, that permission check always fell through to `hasPermission()`'s "unknown permission key" fallback of `false`, for **every role including Administrator**. Succession Planning was permanently inaccessible in the original tool; nobody could ever have used it. This port gives it its own correctly-wired key, `succession_manage` (Admin/Manager), in `config/permissions.js`, instead of silently reusing `reports_view` — reusing it would have coupled two unrelated Permission Matrix rows together (unchecking a Manager's Reports access shouldn't also lock them out of succession plans).
- `LMSEngine.gs` → `src/models/Course.js` + `Enrollment.js` + `Certificate.js`, `src/controllers/trainingController.js`, `views/training/*` — a lightweight Learning & Development tracker (does **not** host course content, same scope note as the original): a course catalog (viewable by everyone, matches `getAllCoursesSafe()`'s open read), enrollment tracking, and certificate issuance. Marking an enrollment "Completed" auto-issues a certificate, same chain as the original's `updateEnrollmentStatus()` → `createCertificate()`. Certificates aren't PDFs — a printable page (`views/training/certificate.ejs`, with a dedicated print stylesheet that hides the sidebar) the employee can print or save as PDF from their browser, exactly as the original intended (`getMyCertificatesSafe()` was always meant to back an in-browser printable view, not a generated file).
- My Profile's "My Trainings" placeholder from Phase 4A/4B is now wired to real data (this employee's enrollments + earned certificates, with a link to each certificate's printable page); My Work's "Pending My Approval" panel now also lists Performance Reviews awaiting the signed-in employee's acknowledgement.

Deferred within 4D, same email-provider reasoning as everywhere else: notifying an employee by email when a goal/review is created, when they're enrolled in training, or when they earn a certificate — all recorded in the audit log instead.

### Phase 4E — Benefits, Wellness, Policy Ack, Letters, Employee Documents (done)

Reading `LetterEngine.gs` and `EmployeeDocumentEngine.html` closely (rather than assuming from their names) turned out to change the earlier plan for this sub-phase — see the two deviation notes below. Nothing here waited on the deferred `PreOnboardingDetailEngine.gs` infrastructure after all.

- `BenefitsEngine.gs` → `src/models/BenefitEnrollment.js`, `src/controllers/benefitsController.js`, `views/benefits/*` — tracks who's enrolled in which company benefit (health insurance, retirement, etc.); a benefits *administration* record, not a claims processor, same scope note as the original. Every route is HR-team gated (`requireHRTeam`), matching the original's `requireHRTeam()` calls on every function in `BenefitsEngine.gs` exactly — unlike Leave/Recruitment/Goals, this list was never open-read. Self-service viewing is through My Profile's new "My Benefits" section (`getMyBenefitsSafe()`'s equivalent).
- `WellnessEngine.gs` → `src/models/WellnessProgram.js` + `PulseSurvey.js` + `PulseResponse.js` + `Kudos.js`, `src/controllers/wellnessController.js`, `views/wellness/*` — three lightweight pieces: a Wellness Programs calendar (open read, `wellness_manage` to create); single-question Pulse Surveys, answered **anonymously by design** (no employee/user field is ever written against a `PulseResponse`, matching the original exactly — creating a survey is `wellness_manage`, viewing results is `reports_view`, same split as the original); and a Kudos peer-recognition wall (open read, `kudos_give` to post — every role, by default).
- `PolicyAcknowledgmentEngine.gs` → `src/models/Policy.js` + `PolicyAcknowledgment.js`, `src/controllers/policyController.js`, `views/policies/*` — IT-team defines policies (`requireITTeam`, matching `createPolicy()`), every employee acknowledges them (self-service, ownership-checked — you can only acknowledge as yourself, and only once: enforced by a unique compound index on policy+employee as well as the same "already acked" check the original had), and IT/HR can pull a compliance report of who has/hasn't (`requireITTeam`, matching `getPolicyComplianceSafe()`). My Profile now shows a "policies awaiting your acknowledgment" banner, wired to `getMyPendingPolicyAcknowledgmentsSafe()`'s equivalent.
- `LetterEngine.gs` → `src/models/Letter.js`, `src/controllers/lettersController.js`, `views/letters/*`, plus a new generic key/value `src/models/Setting.js` + `src/utils/settings.js` (port of `Config.gs`'s `getSetting()`/`setSettingInternal()`, backed by a Mongo collection instead of Script Properties) for the HR-editable letter templates. **Correction to the Phase 4 plan**: earlier notes in this file assumed `LetterEngine.gs` needed the same document-storage infrastructure `PreOnboardingDetailEngine.gs` is waiting on — rereading it shows that's wrong. It never stored a file at all: it merged a `{{Placeholder}}` template and immediately emailed the result (the email inbox WAS the record). With no email provider (same deferral as everywhere else), every generated Offer Letter / Appointment Letter / No Dues Certificate is instead saved to the new `Letter` collection and rendered as a printable page (`views/letters/view.ejs`), same "record instead of emailing" pattern as the training Certificate. Generating an Offer Letter still auto-checks off "Offer Letter Sent" on the candidate's Pre-Onboarding checklist (`markChecklistTaskDone()`, a new small helper alongside `createChecklistIfMissing()` in `utils/checklists.js`, porting `markPreOnboardingTaskDone()`). Completing a resignation (all 5 clearances "Cleared") now auto-generates a No Dues Certificate the same way, replacing the emailed one.
- `EmployeeDocumentEngine.html` → `src/models/EmployeeDocument.js`, `src/controllers/employeeDocumentController.js`, `views/documents/*` — per-employee document storage (ID proofs, certificates, signed offer letters). **Architecture deviation, not a deferral**: the original stored files in a Google Drive folder and kept only a Drive URL in the sheet. This app has no file-hosting account to point at, and the standing rule is zero new third-party accounts of any kind, free or paid. Rather than deferring the whole module (the path taken for `PreOnboardingDetailEngine.gs`'s document vault and `AttachmentEngine.gs`, which have the same problem and remain deferred), the file bytes are stored directly inside the MongoDB Atlas cluster this app already has — see `models/EmployeeDocument.js`'s own comment for the full reasoning and the tradeoff (a 3MB-per-file cap, tighter than the original's 10MB, to protect the shared 512MB free-tier database). Same ownership rule as the original: any employee can upload/view their own documents; the HR team can upload/view for anyone.
- My Profile gained three more sections this sub-phase: My Benefits, My Documents (with a link to the full Documents manager), and a pending-policy-acknowledgment banner.

Deferred within 4E, same email-provider reasoning as everywhere else: notifying every active user when a new policy is published, notifying an employee on benefits enrollment, and notifying a Kudos recipient — all recorded in the audit log instead.

### Phase 5A — IT Helpdesk, Asset Allocation, IT Clearance, Access Requests

- `ITHelpdeskEngine.gs` → `src/controllers/helpdeskController.js`, `views/helpdesk/index.ejs` (`/helpdesk`, IT-team gated). The original's engine defines `getOpenIncidentsSummarySafe()`/`getPendingRequestsSummarySafe()` ("a focused work queue... surfaces it filtered and prioritized specifically for IT staff to triage quickly") but the live `ITManagement.js.html` tab that's actually wired up never calls them — it just links out to Incidents/Requests/Dashboard with a note that helpdesk data "lives entirely in IT Service Management... to avoid any duplication." This port builds what the engine's own comment describes: a stat-card summary (open/critical/unassigned incidents, pending requests) reusing the existing `Incident`/`ServiceRequest` collections, plus the same links-out — the more useful of the two versions, and a deliberate improvement over the shipped original rather than a literal copy of dead code.
- `ITAssetAllocationEngine.gs` → `src/models/ITAllocation.js`, `src/controllers/itAllocationController.js`, `views/it-allocation/*.ejs` (`/asset-allocation`, IT-team gated). Genuinely real, not a checkbox: allocating assets here calls a new `issueAssetInternal()` (extracted from `assetController.js`'s existing `issueAsset` route handler, same internal/public split pattern used throughout this migration) against the real Asset Register, so the asset genuinely becomes assigned with full Asset History logging. "Awaiting IT Provisioning" queries the Pre-Onboarding checklist directly for the "IT Asset Provisioning Requested" task (added in Phase 4A); allocating marks that task Done via `markChecklistTaskDone()` (Phase 4E). The original also emailed the employee what they'd been allocated — skipped, no email provider (see the Employee Documents/Letters entries above).
- `ITClearanceEngine.gs` → `src/models/ITClearanceRecord.js`, `src/controllers/itClearanceController.js`, `views/it-clearance/*.ejs` (`/it-clearance`, IT-team gated). Pulls the employee's actually-assigned assets straight from the Asset Register (not a free-text checklist); submitting formally returns each selected one via a new `returnAssetInternal()` (same extraction as above). `resignationController.js`'s `updateClearance` route handler was split into an internal `updateClearanceInternal(resignation, type, status, actorId)` + a thin route wrapper, exactly per the comment already left in that file back in Phase 4E ("Once IT Clearance (Phase 5) exists it can post to this same endpoint from its own IT-team-gated screen") — so IT Clearance updates the same Resignation record HR's Resignations tab shows, without needing HR-team access itself. ## Phase 9 — Robotics-Company Additions: Calibration Scheduling, Fleet Reliability, Safety Reporting, Equipment Booking (done)

Unlike every phase before it, nothing here ports an original `.gs`/`.html` file — the 116-file project (and the 4 gaps Phase 8 closed) is fully covered as of Phase 8. This phase is genuinely new scope, requested directly: the company running this app is in the service-robotics industry, with departments (Robotics, Electrical, Electronics, Production, and others alongside the HR/IT/Admin ones already covered) whose day-to-day work involves physical hardware an IT-department-shaped ITSM tool has no concept of. All four additions below reuse an existing module's model/pattern rather than inventing a new one, and all four are free-tier/no-new-account compatible, same standing constraint as everything else in this project.

- **Calibration / Maintenance Scheduling** — `Asset` gained `hardwareType` (IT Equipment/Robot Unit/Sensor/Actuator/Controller/Battery/Other, defaulting to "IT Equipment" so every pre-Phase-9 asset keeps behaving exactly as before), `maintenanceIntervalDays`, `lastMaintenanceDate`, and `nextMaintenanceDue`. A new `POST /assets/:id/maintenance` (`assetController.logMaintenance()`) logs a service event and rolls `nextMaintenanceDue` forward from the interval, writing an `AssetHistory` entry the same way `issueAsset()`/`returnAsset()` already do. Shown as a new "Calibration / Maintenance" panel on the Asset detail page.
- **Fleet Reliability (MTBF) report** — `Incident` gained an optional `relatedAsset` free-text field (same plain-string-link convention as `Problem.linkedIncidents`), with a `<datalist>`-backed autocomplete on the New Incident and Incident Detail forms (`incidentController.listAssetNames()`) so filing a ticket against a specific robot doesn't require memorizing its Asset ID. `reportController.assetReliabilityReport()` groups Incidents by `relatedAsset` and computes Mean Time Between Failures in days — honestly framed as "how often this equipment generates a ticket," since this app has no sensor telemetry to compute real uptime from, same "derived only from what's actually recorded" discipline as every other report on the Reports page.
- **Safety Incident / Near-Miss reporting** — a new `SafetyIncident` model + `safetyController.js` + `views/safety/*`, modeled directly on `Complaint`'s shape (open-submit / Admin-Manager-manage tiers, via two new Permission Matrix keys `safety_submit`/`safety_manage`) rather than folding into Complaints — severity (Near Miss/Minor/Moderate/Severe), an injury-involved flag, and an optional related-asset field need their own reporting surface so near-miss frequency doesn't get diluted into general IT/facilities complaint counts. A successful report also posts to Slack/Teams via the existing `notifyChannels()` (Phase 5E) if a webhook is configured, same no-email-provider-needed pattern as the Phase 7 public intake form and Phase 6's expiry digest.

## Phase 10 — Company-Wide Department Coverage: Sales, Production, Engineering Changes, Logistics, Store, Finance (done)

Like Phase 9, nothing here ports an original `.gs`/`.html` file — this is genuinely new scope. Where Phase 9 gave the robotics-hardware side of the company (Assets, Incidents, Rooms) new capabilities, Phase 10 responds directly to the instruction to make sure "each and every department" named in the company's full list (HR, Logistics, Sales, Technical, Software, Robotics, Electrical, Electronics, Production, Designing, Store, IT Infra, Finance, Admin, Management) gets genuine ease of working, not just IT/HR. Five departments still had literally nothing in the app to use day-to-day — Sales, the hands-on-hardware departments (Production/Robotics/Electrical/Electronics/Technical/Software), Designing/Engineering, Logistics, and Store — plus Finance, which had data (Purchase Orders, Expense Claims) but no roll-up view of it. All additions below are free-tier/no-new-account compatible and follow this codebase's established patterns rather than inventing new ones.

- **Sales Orders** (Sales) — a new `SalesOrder` model (`salesOrderId`, customer, item, quantity, amount, expected delivery, a 7-stage status from Enquiry through Delivered/Cancelled) + `src/controllers/salesController.js` + `views/sales/*` (`/sales`). Modeled directly on `purchaseController.js`'s shape — list + create + inline status-update dropdown, no separate detail page — since a sales order's lifecycle is the same "record it, move it through a small set of statuses" shape as a purchase order, just the outbound mirror of it. New Permission Matrix keys `sales_create` (Admin/Manager/Service Desk/Engineer/Viewer — deliberately open, since any department may need to log an order) and `sales_edit` (Admin/Manager/Service Desk/Engineer) for status changes.
- **Work Orders** (Production, Robotics, Electrical, Electronics, Technical, Software) — rather than building six near-identical modules for six departments doing the same kind of work ("build/assemble/repair this, track its status"), a single new `WorkOrder` model covers all six via a plain free-text `department` field — the exact "one model, a discriminator field" pattern already used for `Checklist.type` and `Room.resourceType` (Phase 9), and governed by the same Master Data "Departments" table as `Incident.department`. Optional `relatedSalesOrder` and `relatedAsset` free-text links tie a work order back to what triggered it and what equipment it's for, without a hard foreign key (same plain-string-link convention used throughout this app). `src/controllers/workOrderController.js` + `views/work-orders/*` (`/work-orders`), with department/status query filters on the list page since one shared module across six departments needs a way to narrow the view. New keys `workorders_create`/`workorders_edit`, same role tiers as Sales.
- **Engineering Change Requests** (Designing, Technical, Software, Robotics, Electrical, Electronics) — a new `EngineeringChangeRequest` model + `src/controllers/ecrController.js` + `views/engineering-changes/*` (`/engineering-changes`), deliberately separate from `changeController.js`'s existing Changes/CAB module: Changes governs IT infrastructure change control (servers, network, systems), while an ECR is a product/design revision to what the company actually builds — different subject matter, same "propose → decide" shape, so the two-tier permission pattern is reused (`ecr_create`, open to the same roles as Sales/Work Orders; `ecr_decide`, Admin/Manager only, mirroring `changes_approve`'s CAB-only decision tier) without merging the two into one confusing module.
- **Shipments** (Logistics) — a new `Shipment` model with a `direction` field (Inbound/Outbound) covering both incoming supplier deliveries and outgoing customer dispatches in one module rather than two, plus carrier/tracking/origin/destination and a 6-stage status (Preparing → Delivered, or Delayed/Cancelled). `src/controllers/shipmentController.js` + `views/shipments/*` (`/shipments`), direction/status query filters on the list, `updateStatus()` auto-stamping `dispatchDate`/`actualDeliveryDate` when a shipment crosses into Dispatched/Delivered so those timestamps don't need a separate manual entry. New keys `shipments_create`/`shipments_edit`, Admin/Manager/Service Desk/Engineer (no bare Viewer tier here, unlike Sales/Work Orders/ECRs — logging a shipment is a Logistics-operations action, not something every department self-serves).
- **Material Requests** (Store) — a new `MaterialRequest` model + `src/controllers/materialRequestController.js` + `views/material-requests/*` (`/material-requests`), letting any department draw against Stock/Inventory (already built in an earlier phase) through a real request-and-issue workflow instead of Store staff manually running Stock transactions on someone's behalf. The key design decision: **issuing a request must actually move stock**, not just flip a status flag — the same "internal function backs a real side effect" principle already established by `assetController.issueAssetInternal()`/`returnAssetInternal()`. `stockController.js` was refactored to extract a new `recordTransactionInternal({itemId|itemName, type, quantity, reason, performedByEmail, actorId})` out of the existing `recordTransaction` HTTP handler (which now just calls it and keeps its own redirect/error-message behavior unchanged), so `materialRequestController.issueRequest()` calls it directly with `type: "OUT"` — a genuine `StockTransaction` record is created and `StockItem`'s derived current-stock calculation reflects it immediately, and it fails loudly (not enough on hand, item renamed/removed) the same way a direct Stock OUT transaction would, before the request is ever marked Issued. New keys `material_requests_submit` (open, same tier as Sales/Work Orders/ECRs) and `material_requests_issue` (Admin/Manager/Service Desk — Store-operations tier, no bare Engineer/Viewer).
- **Finance & Spend Overview report** (Finance) — rather than a whole new ledger module, `reportController.js` gained `financeSpendReport()`, which reuses two datasets that already exist — `PurchaseOrder` (outgoing spend/commitments) and `ExpenseClaim` (reimbursable employee spend, counted only once Approved or Reimbursed, since Pending/Rejected claims aren't real spend yet) — grouped by month into a single new panel on the Reports page. No new model, no new Permission Matrix key: it's gated the same `reports`-visible way every other report on that page already is.
- New "Sales, Production & Logistics" sidebar section (Sales Orders, Work Orders, Engineering Change Requests, Shipments, Material Requests), all open-list-view same as every other module in this app — anyone signed in can see what's in flight; the permission keys above gate creation/status changes/decisions/issuing, not visibility.
- All five new list-detail modules deliberately follow the lighter "Purchases/Requirements/Complaints" pattern (list + inline status update via a redirect-with-`?message=` query param) rather than the heavier Incident/Request/Problem/Change/Asset/CMDB pattern with a separate detail page, comments, attachments, and audit-trail display — none of these five needed a multi-person comment thread or file attachments to be genuinely useful, and keeping them lighter kept this phase's scope controlled given how many departments it already touches in one pass.
- Full three-pass verification re-run: 202 modules load with 0 failures (up from 187), 115 fixtured views render with 0 failures (up from 105) — the ten new views (`sales/list.ejs`, `sales/new.ejs`, `work-orders/list.ejs`, `work-orders/new.ejs`, `engineering-changes/list.ejs`, `engineering-changes/new.ejs`, `shipments/list.ejs`, `shipments/new.ejs`, `material-requests/list.ejs`, `material-requests/new.ejs`) and the updated `reports/index.ejs` fixture all render cleanly. ## How to port each module (the pattern used for Incidents)

1. Read the original `*Engine.gs` file in `../original-source/` — note the sheet's exact columns and every function's validation/permission checks.
2. Add or adjust the Mongoose model in `src/models/` to match those columns.
3. Add the module's actions to `src/config/permissions.js` (they're already listed in the full `DEFAULT_PERMISSIONS_MAP` you can find inside `../original-source/Security.gs` — Phase 1 only copied the ITSM-relevant subset).
4. Write a controller in `src/controllers/` porting each function 1:1 (same validation, same audit log calls, same notification points).
5. Write routes in `src/routes/`, guarded with `requirePermission()`/`guard()` matching the original's checks.
6. Write EJS views under `views/` following the Incident views as a template for consistent look and feel.
7. Add a smoke test following `src/scripts/smoketest.js`'s pattern before calling the module done.
